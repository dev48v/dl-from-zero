🧮 Batch norm at inference — in training the layer normalises each row with the statistics of the batch it happens to be in; at inference there is no batch, so it uses a running average collected during training. Those are two different functions, and the layer swaps one for the other silently. Every score here is a real forward pass over an enumerated 512-row population, so the errors are exact means rather than estimates. 🔴 Same input, same weights, two answers: train mode and eval mode differ by an RMSE of 0.3219, and the running estimate of the variance is off by as much as 5.36 on one feature. 🔴 Raising the batch size makes inference WORSE. The gap between the running statistics and the true population statistics is 0.1036 at a batch of 8 and 1.3771 at 256 — 13× worse — because momentum needs many updates and a big batch gives it two. The knob that makes training more stable makes the thing training hands to production less accurate. 🔴 And all four properties a batch-norm test can assert without a second implementation hold in both cases, including on sorted data where the train/eval divergence doubles to 0.6648.

No sampling anywhere. The input set is a fixed, enumerated population of 512 rows, so “the error at inference” is the exact mean over every row rather than an estimate from a test split. The oracle — what the layer would do if it knew the population statistics — is computable for the same reason.

Turn the two knobs

1. Bigger batches, worse inference

The intuition is that a larger batch gives a better estimate of the mean and variance, so the running average should be better too. The first half is true. The second does not follow, because the running average is an exponential moving average over updates, and a bigger batch means fewer of them.

🔴 The best setting for the inference statistics is a batch of 8, not the largest available. At 256 there are only two updates in the whole pass and the running estimate never leaves its initialisation, giving 13× the error. Two things move in opposite directions as the batch grows — each batch's statistics get more accurate, and the number of times that accuracy is folded in gets smaller — and the second wins.

2. Momentum is not a smoothing preference

It is the other half of the same arithmetic. With m momentum and k updates, the initial value still carries weight mk — and at a batch of 256, k is 2.

The pairing matters more than either number: a high momentum with few updates leaves the running variance sitting near its initial value of 1, which is why the worst per-feature variance error reaches 5.36 on features whose real variance is nowhere near 1.

3. The properties hold either way

Here is everything a batch-norm implementation can assert about itself without a second implementation to compare against, checked on shuffled data and on data sorted by its first feature — which is what you get whenever rows arrive grouped by class, by user or by time.

All four pass in both. Meanwhile the train/eval divergence goes from 0.3219 to 0.6648 — it doubles — because sorted batches are not exchangeable, so each batch's statistics describe its own slice of the data and not the data. Nothing in the four properties mentions the order of the rows, and the layer has no way to notice.

What this is and is not

This is one batch-norm layer with fixed gamma and beta over a single pass. It is not a trained network: there is no optimiser and no backward pass, because the finding does not need one — the divergence between train mode and eval mode is a property of the normalisation arithmetic, not of learning. What that leaves out is real: in a trained network the following layers adapt to whatever the normaliser hands them, which can absorb some of this and can also compound it. The claim here is about the layer.

How it works

// training: the batch it happens to be in
const { mean, varr } = batchStats(batch);
out = gamma * (x - mean) / sqrt(varr + eps) + beta;

// inference: one fixed affine map, from an average over UPDATES
runMean = m * runMean + (1 - m) * mean;   // k updates, not k rows
out = gamma * (x - runMean) / sqrt(runVar + eps) + beta;

The running variance uses the unbiased correction while the batch normalisation itself uses the biased one, which is what the reference implementations do — another small way the two paths are not the same function.
