DEEPLEARNINGFROMZERO · DAY 69

🗄️ The KV cache — an exact optimisation that gets blamed for everything. Generating token n re-derives the keys and values of tokens 1…n−1 that the previous step already computed, so store them. This page builds a small transformer with a hand-written forward and backward pass and shows the cache is not an approximation: a cached decode reproduces a full recompute to exactly 0.0 across 432 configurations per numeric format — 1,296 in all — in float64 and in bfloat16, under two summation orders. The reason is a stronger statement than the cache itself — causality freezes the residual stream at every earlier position, measured at 0.0 per layer, and turn causality off and the same cache is wrong from layer 2 onwards while layer 1 stays exact. Then the two things everyone says. “It makes generation linear instead of quadratic”: it removes one factor of n, measured slopes 2.992 → 1.995, and per token it is flat only up to a context of 6d — 4,608 tokens for GPT-2 small, computed not quoted. And “the cache changed my output”: the standard one-step logit check catches 4 of 8 real cache bugs, misses half of the ones that changed the generated text, and ranks them at AUC 0.605 against a chance value of 0.500 — while the same comparison run at every step catches 8 of 8 and needs no tolerance at all. Pure vanilla JavaScript, one file, no build step.

A decoder-only transformer — pre-norm, RMSNorm, SiLU MLP, learned absolute positions, 1,432 parameters — with two independent implementations of the same function: a full forward pass over the whole prefix, and a prefill plus one-token-at-a-time decode over a cache. Every number below is the difference between them. The output matrix is deliberately not tied to the embedding (that was Day 67) so the position experiments here measure one thing at a time.

The same numbers, twice


      
Generating text one token at a time, the naive loop looks like this:


      
for step in 1..n:
    logits = model(sequence)      # the WHOLE sequence, every time
    sequence.append(argmax(logits[-1]))


      
Inside model, every layer projects every position into a query, a key and a
      value, and the attention at position i reads the keys and values of positions
      0…i. Step t therefore recomputes the keys and values of every token
      that step t−1 already computed. The KV cache stores them instead:


      
prefill: run the prompt once, KEEP every layer's K and V
decode:  for each new token, compute ITS k and v, append them,
         and attend over the whole stored buffer


      
The theorem is about causality, not about caching


      
Storing a value is only correct if the value does not change. The key and value of
      position i at layer ℓ are a function of the residual stream at position
      i entering layer ℓ, and under causal attention that stream depends only on
      positions ≤ i. Appending a token at position i+1 therefore cannot move
      it. Measured on this page, appending a token moves the stream, the keys and the values at
      every earlier position and every layer by exactly 0.


      

        
Turn causality off and the boundary is visible: layer 1's keys still
        move by exactly 0, because they depend only on the embeddings, while layer
        2's move by 1.9e-1. A one-layer bidirectional model is therefore still
        exactly cacheable end to end (measured 0.0e+0); a two-layer one is not (1.8e-1). The cache
        is a consequence of the mask, and the depth at which it breaks is the depth at which
        information can flow backwards.

      


      
So the cache is not an approximation and not a trade-off. A cached decode and a full
      recompute are the same function, and this page asserts it the strongest way available:
      bit equality, exactly 0.0 over 432 configurations of seed, depth, head
      count, prompt length, step count and summation order, in each of three numeric formats
      — 1,296 runs, and the generated token strings match in all of them.


      
“It makes generation linear” — it removes one factor of n


      
Counting multiply-accumulates rather than estimating them, generating n tokens
      costs


      
no cache:  (L·perTok + dV)·n(n+1)/2  +  L·d·n(n+1)(n+2)/3      -> CUBIC
with cache: n·(L·perTok + dV)          +  L·d·n(n+1)            -> QUADRATIC


      
Measured log-log slopes from those closed forms, between n=106 and
      107: 2.992 without and 1.995 with. The cache does
      not remove the quadratic; it removes the
      recomputation, which is a separate factor of n. Attention over a growing cache is
      still linear work per token, so the total is still quadratic in the length.


      

        
And yet “linear” is not simply wrong — it is right in
        the regime the phrase was coined in. A cached decode step does
        L·perTok work that does not depend on the context and
        2·L·d·t that does, so the per-token cost is
        flat until the second term catches the first. That happens at
        t = perTok / 2d, which for the usual non-gated 4d MLP is exactly
        6d — 4,608 tokens for GPT-2 small, 9,600 for GPT-2 XL — and a
        gated MLP shifts it a little, 24,704 for Llama-2 7B. Below the crossover the measured slope
        is 1.002. Anyone who said
        “linear” in 2019 and had a 1,024-token window was making a correct measurement
        about their own regime.

      


      
The cost that moved from compute to memory


      
The cache is 2 · L · n_kv · d_head numbers per token,
      and nothing about the content changes that. Computed from the published architectures:
      36 KB per token for GPT-2 small, 512 KB for Llama-2 7B,
      2.5 MB for a hypothetical 70B with full multi-head attention. Divide the
      weights by the per-token cache and you get the context length at which one sequence's cache
      equals the entire model: 6,749 tokens for GPT-2 small,
      25,711 for Llama-2 7B.


      
Grouped-query attention is the answer to that, and its arithmetic is worth stating
      exactly, because two thirds of it is usually stated wrongly:


      
GQA with 8 KV heads instead of 64:
  attention FLOPs   x 1.00      <- unchanged, and this is an identity
  cache bytes       / 8
  MACs per byte     x 8         <- 0.5 -> 4.0


      

        
Every query head still attends over a full-width key, so GQA saves no
        arithmetic whatsoever — the FLOP identity is asserted on this page rather than
        described. What it saves is bytes moved, and a decode step at 0.5 MACs per byte is
        not a compute problem, it is a memory-bandwidth problem. GQA does not make attention
        cheaper; it makes it possible to keep the machine busy.

      


      
The interesting part: the test everybody writes


      
The cache is exact, so any deviation is a bug, and the standard check is to compare cached
      logits against a full recompute. Almost always on one step. Eight realistic bugs,
      each one changed line:


      
stale      attend before appending, so the token cannot see itself
vstale     append k, re-use the previous v
alias      every layer writes into layer 0's buffer
posoff     the position index is one behind
ring       ring buffer, write at len % cap
freeze     the buffer stops growing after the first decode step
evict      a sliding window nobody asked for
posfrozen  the position index stays at the prompt length


      
The first four are wrong at the first decode step. The last four are
      bit-identical at the first decode step — exactly 0.0, not 1e-12 —
      because at step 1 the cache is still just the prefill and every implementation agrees about
      it. They are bugs in the cache's growth, and step 1 is the one step where nothing
      has grown yet.


      

        
🔴 posfrozen — using the prompt length as the
        position offset instead of the running cache length, which is the single most common way to
        get this wrong when resuming from a cache — is exactly 0.0 at the
        first decode step and changes the generated text in 100% of runs. The check
        that would have caught it is the same check, run one step later.

      


      
Scored as a detector over 240 cases, the one-step check has a recall of
      0.500: it flags half of the bugs that changed the output and misses the other half
      entirely. As a ranker of “did this change the text” it scores AUC
      0.605 against a chance value of 0.500. Comparing every step instead: recall
      1.000, AUC 1.000, and no tolerance needed anywhere, because
      the correct implementation is bit-identical.


      
Two rows that cut the other way


      
Being visible is not the same as mattering, and the zoo makes both mistakes available:


      
stale   step-1 deviation 0.146   output changed in   0% of runs
evict   step-1 deviation 0.000   output changed in   0% of runs
        (all-steps deviation 0.254 -- it IS a bug, it just never bit)


      
stale moves the logits immediately and never moves a token, because the
      trained model's smallest top-2 margin over 540 positions is 5.50. A bug can
      be real, visible in the logits, and invisible in the output. And evict quietly
      drops the oldest key once the buffer passes its capacity, which on a task that never needs a
      key that old is not a symptom at all — a sliding window is only a bug if something
      needed the window.


      
And the explanation I expected to confirm, which did not survive


      
The usual account of “the KV cache changed my output” is floating-point
      reduction order: a batched prefill and a single-token decode are different shapes, real
      kernels sum tiled rather than sequentially, and the last bits differ. This page implements
      both orders and measures the whole chain. The order really does change the answer — and
      then:


      
on the near-tied model             delta, cached   delta, NO cache   changed: cached / control
float64 throughout                    4.0e-15          3.3e-15            0 / 24    0 / 24
bfloat16 stored, float64 accumulator   0.0e+0           0.0e+0            0 / 24    0 / 24
bfloat16 stored AND accumulated          4.02             4.04            3 / 24    2 / 24


      

        
🔴 Storing everything in bfloat16 and accumulating in a wider type
        — which is what every real kernel does — makes the two summation orders agree
        exactly, at 100% of positions. Reducing the precision removed the
        discrepancy, because a 1e-16 disagreement lands on the same bfloat16 grid point. It is the
        accumulator's precision that makes order matter, not the shape of the
        reduction, and the page was written expecting the opposite.

      


      
The control is the part that settles it. In the one regime where order does change tokens,
      it changes them in 2 of 24 runs with no cache anywhere — two
      full recomputes that differ only in how they add up — against 3 of 24 for the cached
      run. Same phenomenon, same size, and the cache stays bit-exact in all three formats. On the
      fully trained model nothing changes at all in any format, because its smallest top-2 margin is
      5.83 and a rounding difference has to clear that to move an argmax. Whatever changed the
      output, it was not the cache.


      
Where a cache does change the answer


      
Not in inference. In training, if a cached prefix is reused: its keys and values
      arrive as constants, so no gradient flows into them, and the gradient you apply is not the
      gradient of the loss you evaluate. Both are computable here, and the true one is checked
      against central differences to 3.2e-8 first.


      
cached prefix   cosine with the true gradient   relative error
  2 of 12                 0.942                       0.328
  6 of 12                 0.857                       0.498
 10 of 12                 0.854                       0.517


      
It is still a descent direction — the cosine stays positive, which is why the loss
      curve looks fine — and it costs something real: training with the detached gradient at
      a prefix of 6 of 12 reaches a held-out suffix loss of 1.346 against
      0.059 for the true gradient, 22.8× worse.

🔨 How it is built


      
1. Two code paths that must agree to the bit

      
forward(M, tokens, {cache})   // all T positions, LAYER-major, optionally fills the cache
decodeStep(M, cache, tok, pos) // ONE position over the cache

      
Bit equality is the whole instrument, so it has to be reachable, and that constrains the
      implementation. Both paths run the same loops in the same order: matvec
      accumulates input-major so every output's summation order is ascending regardless of how many
      positions are in flight; attention sums j ascending in both; the softmax subtracts
      the max over the same set in the same order. Get any of that wrong and the identity becomes
      "agrees to 1e-16", which is a weaker claim and a worse test.


      
2. Layer-major, on purpose

      
for each layer:  compute K,V for ALL positions, then attend      // works causal AND not
// position-major would also work -- but only for causal attention,
// and the non-causal control is the page's best evidence

      
The non-causal run is what turns "the cache works because of causality" from an
      explanation into a measurement, so the code has to be able to run without the mask.


      
3. Every bug is one changed line

      
// correct
Kl.push(k); Vl.push(v); attendLen = Kl.length;

// 'ring'
if (Kl.length < cap){ Kl.push(k); Vl.push(v); }
else { const w = Kl.length % cap; Kl[w] = k; Vl[w] = v; }

// 'freeze'
if (cache.steps <= 1){ Kl.push(k); Vl.push(v); }

      
Parameterising the bugs rather than describing them is what makes "four of them are
      bit-identical at step 1" a number instead of an argument. It also keeps them honest: they are
      each one line, they are each something a person would actually write, and two of them turn
      out not to change the output at all.


      
4. Precision as two separate knobs

      
q   : the format values are STORED in        (applied after every matvec, norm, softmax)
ACC : the format the accumulator runs in     (applied after every += inside a dot product)

      
This split is the page's one real surprise. With q = bfloat16 and
      ACC = float64 the two summation orders agree exactly; with both in bfloat16 they
      differ by whole ulps. Had the two been one knob, the conclusion would have been the usual
      hand-wave about low precision being noisy, which is the opposite of what happens.


      
5. Cost in closed form, checked against the loop

      
costs(cfg, n)      // step by step, for the table
costTotals(cfg, n) // closed form, for exponents at n = 10^7
assert(loop / closed_form - 1 < 1e-12)   // at n = 300

      
The slopes need lengths no loop should run, and a closed form nobody checks is just an
      algebra mistake waiting to be quoted. So both exist and they are asserted equal.


      
6. The backward pass exists so the model is real

      
h = x + attn(rmsnorm(x));  h = h + mlp(rmsnorm(h));  logits = rmsnorm(h)·Wu
// hand-written backward through the softmax, the RMSNorm and both residuals
// worst relative error against central differences: 3.2e-8 over 24 tensors

      
"The output changed" is only interesting for a model whose output means something, so the
      model is trained (lag-3 copy: repeat the token three places back — chosen because it
      forces attention onto a key that is neither the current position nor the first, so an old
      cache entry is load-bearing) from 3.098 to 0.00082 nats against a chance value of 2.079.


      
7. Two gradients, deliberately

      
backward(..., {from: k})                   // the true gradient of the suffix loss
backward(..., {from: k, detachBefore: k})  // dK[j], dV[j] dropped for j < k

assert(relErr(true, central differences) < 1e-6);   // 3.2e-8
assert(relErr(detached, central differences) > 1e-3);  // it is not the gradient of anything

      
Straight out of Day 68: asserting that the shortcut disagrees with finite
      differences turns "prefix caching biases the gradient" from a claim into a test that fails if
      it is ever false.


      
8. What the tests pin

      
// the identity, as bit equality and over a grid
assert(cacheDeviation(...).worst === 0);                 // exactly, not to a tolerance
assert(exactGrid().worst === 0 && tokenMismatches === 0); // 432 configurations

// the reason, and the boundary of the reason
assert(freeze(causal).dK === 0 for every layer);
assert(freeze(non-causal)[0].dK === 0 && [1].dK > 0);     // layer 1 exact, layer 2 not
assert(nonCausalCost(L=1) === 0 && nonCausalCost(L=2) > 1e-6);

// the cost claim, both ends of it
assert(2.9 < slope_plain <= 3.0 && 1.9 < slope_cached <= 2.0);   // asymptotically
assert(slope_cached(n=8..64) < 1.05);                            // and flat below 6d
assert(crossover === 6d);

// GQA, as identities
assert(attention_flops(gqa) === attention_flops(mha));
assert(cache_bytes(mha) / cache_bytes(gqa) === 8);
assert(intensity(gqa) / intensity(mha) === 8);

// the diagnostic, scored rather than trusted
assert(exactly 4 of the 8 bugs are bit-identical at step 1);
assert(all 8 are caught by an all-steps comparison);

// and the surprise, so it cannot be quietly reverted
assert(bf16-stored/f64-accumulated order difference === 0 at 100% of positions);
assert(bf16-accumulated order difference > 1e-3);
assert(the cache is exact in ALL THREE formats);

      
The last group is the one worth stealing. The page set out to explain output changes by
      reduction order, and the measurement said the standard accumulator erases it. Asserting the
      erasure means the page cannot drift back to the story it wanted to tell.
