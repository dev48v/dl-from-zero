DeepLearningFromZero · Day 62

⬍ Transposed convolution — every encoder throws resolution away on purpose, and every decoder has to put it back. Segmentation masks, autoencoder reconstructions, GAN samples, diffusion decoders, super-resolution: all of them need an operator that takes a small feature map and returns a bigger one, with learnable weights rather than a fixed interpolation rule. The operator that got invented for that job is almost universally mis-named. It is called deconvolution, and it does not deconvolve anything — it does not invert the convolution, it only reproduces its shape. What it actually is, exactly and with no hedging, is the transpose of the convolution matrix. Write a convolution as a matrix — it is linear, so it has one, a sparse banded O×I thing whose rows are shifted copies of the kernel — and then y = Cx is the convolution and x′ = Cᵀy is the transposed convolution. That is the whole definition, and this page builds C explicitly and checks it. Two consequences fall straight out. First, CᵀC ≠ I — the page measures how far off it is — so deconvolution is simply the wrong word. Second, and far more useful: ∂L/∂x = Cᵀ(∂L/∂y), which means the backward pass of a convolution IS a transposed convolution, and the backward pass of a transposed convolution is a plain convolution. Frameworks implement one and get the other for free. The strongest way to see it is the adjoint identity ⟨conv(x), y⟩ = ⟨x, convᵀ(y)⟩, which holds here to 2.1e−13 across every configuration the sliders can reach — an identity a merely plausible-looking implementation cannot fake. Then the part that bites people in production: the checkerboard artifact. Its cause is not mysterious and not a training problem — it is uneven overlap (Odena, Dumoulin & Olah, 2016). Each input element sprays the whole kernel into the output; when k is not divisible by s the number of kernel taps landing on an output position is periodic with period s, and that periodic gain is the checkerboard, visible before a single gradient step. This page counts those taps live, exactly, and shows the histogram flatten the instant k % s == 0 — and then shows the sharper truth that an even tap count is not an even gain, because a learned kernel can still be unbalanced across phases. So the fixes are compared honestly: k divisible by s, resize-then-convolve (why it is the safer default), and sub-pixel convolution / PixelShuffle — proved here to be an exact permutation of elements, and made artifact-free at initialisation by ICNR. Below, three real decoders with hand-written backward passes train live in your browser and are measured against each other. 257–633 parameters, no libraries, 48,798 assertions checked in Node against an independently built matrix, brute-force tallies, the adjoint identity and central finite differences, across 48,960 swept configurations.

The cause, counted exactly: how many kernel taps land on each output position

Forget images for a moment. Feed a row of ones through a transposed convolution whose kernel is also all ones. The output is the tap count — nothing else is happening. Input element n writes to output positions n·s … n·s+k−1, so position t collects one tap for every kernel index j with j ≡ t+p (mod s). That congruence is the entire theory: the count is periodic with period s, and it is constant if and only if k divides evenly by s.

⚠️ This is why “deconvolution” is the wrong word. A genuine deconvolution would recover x from y, which needs C⁻¹ — and for a strided convolution C is not even square, so no inverse exists. The transpose only guarantees that the shape comes back. The tile above measures how far CᵀC is from the identity; it is not close, and it is not supposed to be. The transposed convolution is the gradient of the convolution

If y = Cx then ∂L/∂x = Cᵀ(∂L/∂y). There is no separate backward kernel to write: the backward pass of conv is convᵀ and the backward pass of convᵀ is conv. That is not an analogy, it is the same array of numbers read in the other direction — a scatter where the forward pass did a gather. The check below runs live: an upstream gradient goes through the hand-written backward pass, and separately through a central finite difference of the real loss, on freshly initialised weights.

The other way to implement it — and why nobody actually does

Textbook route: insert s−1 zeros between the input elements, pad by k−1−p, then run an ordinary stride-1 convolution with the kernel flipped. It gives bit-identical results to the direct scatter — and it is a terrible implementation, because you have just materialised an array that is mostly zeros and then multiplied all of them. Real kernels scatter or gather and never build it. Both routes run below on the same data.

Output-size arithmetic — and the ambiguity output_padding exists to resolve

Forward: o = ⌊(i + 2p − k)/s⌋ + 1. Transposed: o = (i−1)·s − 2p + k + output_padding. That floor in the forward direction is a genuine loss of information: with stride s, exactly s different input lengths produce the same output length, so the transpose cannot know which one to return. output_padding is you telling it. Sub-pixel convolution — upsampling with no arithmetic at all

Shi et al.’s ESPCN trick: do the convolution at low resolution but produce r times as many channels, then interleave those channels into space. PixelShuffle / depth-to-space is a pure re-indexing — no multiplies, no adds, every value moved exactly once. 💡 ICNR is the part worth stealing. A sub-pixel layer has r independent sub-kernels producing the r interleaved outputs; initialise them independently and they disagree from step zero, which is a checkerboard. ICNR (Aitken et al., 2017) initialises all r sub-kernels to the same values, so the layer starts out as an exact nearest-neighbour upsample — verified above to 1e−14 — and training moves away from that smooth starting point only where the data pays for it. There is nothing to unlearn.
Four ways to make a feature map bigger
Transposed convolution
One scatter, k²CinCout parameters, cheapest FLOPs of the three because the multiplies happen at the low resolution. Learns its own upsampling. Prone to checkerboarding unless k % s == 0 — and even then only the tap count is guaranteed even, not the gain.
Resize + convolution
Nearest or bilinear upsample, then a stride-1 conv. Identical parameter count, s²× the multiply–adds in 2-D because the convolution now runs at full resolution. The interpolation is uniform by construction, so there is no phase structure for the conv to inherit. The safe default, and what most modern decoders use.
Sub-pixel / PixelShuffle
Convolve at low resolution into r² channels, then depth-to-space. Same FLOPs as the transposed conv, no zeros anywhere, and the rearrangement is free. Still checkerboards at init unless you use ICNR. Standard in super-resolution and in several diffusion decoders.
Plain interpolation
Nearest or bilinear with no convolution after it. Zero parameters, zero artifacts, and zero ability to invent detail — it can only blur what is already there. Useful as the honest baseline every learned upsampler should be measured against, and as the skip path in a decoder.

The headline nobody expects: a transposed convolution has exactly the same number of parameters as the convolution it transposes — it is the same tensor. What differs is where the arithmetic happens. A transposed convolution is one loop with the indices swapped — about forty lines including the size arithmetic. Below is the exact runnable core the LOOK tab uses: the forward convolution, its explicit matrix, the transpose written three different ways that must agree, the tap counter that explains the checkerboard, the two honest alternatives, pixel shuffle with ICNR, and a decoder with a hand-written backward pass.     Write the convolution so its matrix is obvious
    
        
    Start from the definition, not from a library call. Output position n reads input positions n·s + j − p for j in [0,k), with anything out of bounds contributing zero. Written that way, the matrix is right there in the loop: row n of C has the kernel starting at column n·s − p. Everything else on this page is a consequence of that one index expression, so it is worth getting into your fingers. Note this is cross-correlation — no kernel flip — which is what every deep learning framework means by “convolution”, and the flip will come back in step 6 exactly where the maths demands it.
    
        
    def conv1d(x, w, s, p):
    I, k = len(x), len(w)
    O = (I + 2*p - k) // s + 1                 # floor -- remember this
    y = [0.0] * max(0, O)
    for n in range(max(0, O)):
        for j in range(k):
            t = n*s + j - p                    # <-- the ONE index expression
            if 0 <= t < I:
                y[n] += w[j] * x[t]
    return y

def conv_matrix(I, w, s, p):                   # the same loop, materialised
    O = (I + 2*p - len(w)) // s + 1
    C = [[0.0]*I for _ in range(max(0, O))]
    for n in range(max(0, O)):
        for j in range(len(w)):
            t = n*s + j - p
            if 0 <= t < I: C[n][t] = w[j]
    return C
# assert conv1d(x,w,s,p) == C @ x     to 1e-12, for every (I,k,s,p)

    The transposed convolution: the same loop, scattering instead of gathering
    
        
    Take the forward loop and move the accumulation to the other side of the assignment. Where the convolution gathered k input values into one output, the transpose scatters one input value across k outputs. The index expression is character-for-character the same. That is not a coincidence or an analogy — it is what taking a transpose does to a sparse matrix–vector product. Two details that are easy to get wrong: the output length is not derivable from the input alone (step 5), and output_padding genuinely widens the region you scatter into, so those extra positions can and do receive taps.
    
        
    def conv_transpose1d(y, w, s, p, output_padding=0):
    N, k = len(y), len(w)
    O = (N - 1)*s - 2*p + k + output_padding
    out = [0.0] * max(0, O)
    for n in range(N):
        for j in range(k):
            t = n*s + j - p                    # <-- IDENTICAL to the forward
            if 0 <= t < O:
                out[t] += w[j] * y[n]          # scatter, not gather
    return out

# assert conv_transpose1d(y,w,s,p,op) == C.T @ y      exactly
# where C is the matrix for an input of length O.  Not C inverse. C TRANSPOSE.

    The adjoint test — the single strongest check you can write
    
        
    Comparing your transpose against a hand-built matrix is good. This is better, because it needs no matrix and no reference implementation, and it fails loudly for every class of index bug: ⟨conv(x), y⟩ = ⟨x, convᵀ(y)⟩ for all x and y. It is a mathematical identity about adjoint operators, so a wrong implementation cannot pass it by accident. Two sub-cases worth having in the test file: the identity is exactly what says your backward pass is the true gradient, and it holds for the multi-channel version too, where the channel indices also have to transpose. On this page it holds to 2.1e−13 across all 48,384 reachable 1-D configurations.
    
        
    for _ in range(1000):
    I, k, s, p = rand_config()
    x, y, w = randn(I), randn(conv_out_len(I,k,s,p)), randn(k)

    lhs = dot(conv1d(x, w, s, p), y)
    op  = I - ((len(y) - 1)*s - 2*p + k)      # the op that lands back on I
    rhs = dot(x, conv_transpose1d(y, w, s, p, op))

    assert abs(lhs - rhs) / (abs(lhs) + abs(rhs)) < 1e-12

# if this passes for random shapes, your transpose is the adjoint.
# if it fails, the failure is almost always in the padding sign or in op.

    Kill the word “deconvolution” with two lines
    
        
    A deconvolution would undo the convolution: given y = Cx, recover x. That needs C⁻¹, and for any strided convolution C is not square, so no inverse exists — there are strictly fewer outputs than inputs and the information is gone. The transpose reproduces the shape and nothing more. Compute CᵀC and look at it: for a 3-tap stride-2 kernel on an 8-long input the diagonal alone varies by a factor of two, and the off-diagonal entries are not small. Keep this test in your repo; it takes four lines and it permanently settles an argument that otherwise recurs forever.
    
        
    C = conv_matrix(8, w, s=2, p=1)          # 4 x 8 -- not square, no inverse
G = C.T @ C                              # 8 x 8

assert G.shape == (8, 8)
assert not np.allclose(G / G.diagonal().max(), np.eye(8), atol=1e-6)

# the only case where it IS the identity is the degenerate one:
C1 = conv_matrix(9, [1.0], s=1, p=0)     # k = s = 1, p = 0
assert np.allclose(C1.T @ C1, np.eye(9))  # a scalar multiply, transposed

    Output sizes, both directions — and why the inverse is ambiguous
    
        
    The forward formula has a floor in it, and a floor destroys information. With stride s, exactly s consecutive input lengths give the same output length — at k=3, s=2, p=1 both i=7 and i=8 produce o=4. So when you transpose, there is no way to know which one you wanted, and the operator has to be told: that is all output_padding is. It adds to one side of the output shape and is required to satisfy 0 ≤ output_padding < s, because s is exactly how many candidates there are. It is not padding in any meaningful sense and it is not symmetric — a name that has confused people for a decade.
    
        
    def conv_out_len(i, k, s, p):        return (i + 2*p - k)//s + 1      # FLOOR
def convT_out_len(i, k, s, p, op=0): return (i-1)*s - 2*p + k + op

# the ambiguity, demonstrated:
assert conv_out_len(7, k=3, s=2, p=1) == 4
assert conv_out_len(8, k=3, s=2, p=1) == 4        # same output, different input

# so the transpose needs to be told which one to rebuild:
assert convT_out_len(4, 3, 2, 1, op=0) == 7
assert convT_out_len(4, 3, 2, 1, op=1) == 8

# the op that undoes a specific forward pass, in closed form:
def output_padding_for(i, k, s, p):
    o = conv_out_len(i, k, s, p)
    return i - ((o - 1)*s - 2*p + k)              # always in [0, s)

    The zero-insert route — correct, instructive, and a bad implementation
    
        
    The picture everybody draws: insert s−1 zeros between the input elements, pad by k−1−p, and run an ordinary stride-1 convolution with the kernel flipped. It is genuinely equal to the scatter — agreement here is bit-for-bit across 48,384 configurations — and it is a useful mental model for why the operator smears energy the way it does. It is also a bad way to compute it, because you have built an array that is (s−1)/s zeros and then multiplied every one of them. Real kernels never materialise it. The trap: output_padding widens the right-hand pad before the convolution. Stapling zeros onto the end of the result instead is wrong, and wrong in a way that only shows up for op > 0, which is exactly the configuration nobody tests.
    
        
    def convT_via_zero_insert(y, w, s, p, op=0):
    k = len(w)
    d = [0.0] * ((len(y)-1)*s + 1)
    d[::s] = y                                # insert s-1 zeros between elements
    q = k - 1 - p                             # may be NEGATIVE -> crop, not pad
    d = pad_or_crop(d, left=q, right=q + op)  # <-- op goes HERE, not at the end
    return conv1d(d, w[::-1], s=1, p=0)       # flipped kernel, stride 1

# assert convT_via_zero_insert(...) == conv_transpose1d(...)   to 1e-13
# it is exact. it is also 1/s of the useful work. do not ship it.

    Count the taps — the checkerboard, before any training
    
        
    This is the whole diagnosis and it fits in six lines. Output position t receives a tap from kernel index j exactly when j ≡ t + p (mod s), so the number of taps depends only on t mod s. Count them and you get a periodic pattern with period s, constant if and only if s divides k. That periodic gain is the checkerboard — it is present at initialisation, present with a constant input, present with no data at all. It is not an optimisation artifact and it is not noise. In 2-D the pattern is the outer product of the two 1-D patterns, so a 2× imbalance along each axis becomes a 4× imbalance in the corner cells.
    
        
    def tap_counts(k, s):                       # the steady-state, closed form
    return [ (k - 1 - r)//s + 1 if r < k else 0 for r in range(s) ]

tap_counts(3, 2) == [2, 1]     # 2.0x  -- the classic checkerboard
tap_counts(4, 2) == [2, 2]     # 1.0x  -- flat.  the DCGAN fix.
tap_counts(5, 2) == [3, 2]     # 1.5x
tap_counts(4, 3) == [2, 1, 1]  # 2.0x  -- and 4.0x in 2-D
tap_counts(1, 3) == [1, 0, 0]  # some outputs get NO taps at all: holes

assert sum(tap_counts(k, s)) == k          # taps are conserved
assert len(set(tap_counts(k,s))) == 1  ==  (k % s == 0)     # the criterion

# see it with no model at all:
conv_transpose1d([1]*12, [1]*3, s=2, p=1)   # -> 1,2,1,2,1,2,...  THERE it is

    The three fixes, and the one the tap count does not cover
    
        
    Fix one is free: choose k divisible by s. 4/2 and 2/2 are why DCGAN generators look the way they do. But it only evens out the count; with a learned kernel the per-phase gain — the sum of the weights in each residue class — can still be badly unbalanced, and that is a real artifact the divisibility rule does not touch. Fix two is resize-then-convolve: upsample with nearest or bilinear, then a stride-1 convolution. The interpolation is uniform by construction, so there is no phase structure to inherit; you pay s²× the multiply–adds in 2-D and you keep the parameter count identical. Fix three is sub-pixel convolution, below. Training helps, but only partly and not reliably — the measurement on this page shows the artifact moving under training rather than reliably vanishing.
    
        
    # fix 1 -- free, and only half a fix
nn.ConvTranspose2d(cin, cout, kernel_size=4, stride=2, padding=1)   # k % s == 0

def phase_gain(w, s):                       # what divisibility does NOT fix
    g = [0.0]*s
    for j, v in enumerate(w): g[j % s] += v
    return g                                # constant input -> this, exactly
# even tap counts can still give unequal gains for a LEARNED kernel

# fix 2 -- the safe default
nn.Sequential(
    nn.Upsample(scale_factor=2, mode="nearest"),   # or "bilinear"
    nn.Conv2d(cin, cout, 3, stride=1, padding=1),  # SAME parameter count
)                                                  # s^2 x the MACs in 2-D

# fix 3 -- sub-pixel, see step 9
nn.Sequential(nn.Conv2d(cin, cout*r*r, 3, padding=1), nn.PixelShuffle(r))

    Sub-pixel convolution and ICNR — a permutation, initialised to be flat
    
        
    Convolve at low resolution into r² times as many channels, then interleave those channels into space. The rearrangement costs nothing: it is a bijection, every element moved exactly once, and its gradient is the inverse permutation. Test it that way — assert the index map is a permutation and that the sorted multiset of values is unchanged — and you can never get the layout wrong silently. It still checkerboards at initialisation, though, because the r² sub-kernels are independent random draws that disagree from step zero. ICNR fixes that by initialising all r² sub-kernels to the same values, which makes the layer exactly a nearest-neighbour upsample at init — verified on this page to 1e−14. There is then nothing to unlearn.
    
        
    # depth-to-space: out[c][h][w] = in[c*r*r + (h%r)*r + (w%r)][h//r][w//r]
def pixel_shuffle_map(C, H, W, r):
    return { (c, i, j): (c*r*r + (i%r)*r + (j%r), i//r, j//r)
             for c in range(C) for i in range(H*r) for j in range(W*r) }

m = pixel_shuffle_map(C, H, W, r)
assert len(set(m.values())) == len(m)                  # a genuine bijection
assert sorted(out.flatten()) == sorted(inp.flatten())  # values moved, not mixed

def icnr_(weight, r):                       # Aitken et al. 2017
    cout = weight.shape[0] // (r*r)
    base = torch.empty(cout, *weight.shape[1:]); nn.init.kaiming_normal_(base)
    weight.data = base.repeat_interleave(r*r, dim=0)   # all r^2 copies IDENTICAL

# assert: at init, PixelShuffle(conv(x)) == nearest_upsample(conv_base(x))

    The decoder, with the backward pass written out
    
        
    Once you accept that the two operators are each other’s adjoint, the backward pass writes itself — and writing it once is the fastest way to stop finding the subject confusing. The gradient of a convolution with respect to its input is a transposed convolution with the same kernel; the gradient of a transposed convolution with respect to its input is a plain convolution with the same kernel. The weight gradient is a correlation of the input against the upstream gradient in both cases. Notice what changes between the two functions below: only which loop accumulates into which array.
    
        
    def conv_backward(dy, x, w, s, p):
    dx, dw = zeros_like(x), zeros_like(w)
    for n in range(len(dy)):
        for j in range(len(w)):
            t = n*s + j - p
            if 0 <= t < len(x):
                dw[j] += dy[n] * x[t]
                dx[t] += dy[n] * w[j]        # SCATTER  = transposed conv
    return dx, dw

def conv_transpose_backward(dy, x, w, s, p):
    dx, dw = zeros_like(x), zeros_like(w)
    for n in range(len(x)):
        for j in range(len(w)):
            t = n*s + j - p
            if 0 <= t < len(dy):
                dw[j] += x[n]  * dy[t]
                dx[n] += w[j]  * dy[t]       # GATHER   = plain conv
    return dx, dw
# assert both against CENTRAL finite differences on FRESH weights, rel < 2e-5

    Sweep the whole reachable configuration space
    
        
    Random spot checks pass on code that breaks at the edges, and upsampling code has a lot of edges: padding larger than the kernel, a kernel smaller than the stride, an output length that comes out zero or negative, an output_padding at or above the stride. Enumerate every combination the user interface can actually produce and assert that every result is finite and every length matches its formula. Two real bugs on this page were found by exactly this sweep and by nothing else: the zero-insert route mishandled output_padding by stapling zeros on the end instead of widening the right-hand pad, which is silently correct for op = 0; and the “interior” helper could return a slice running past the end of the array whenever the kernel was wide and the output short.

    What to actually use
    
        
    The field largely moved. DCGAN-era generators were transposed convolutions throughout, and the checkerboard in early GAN samples is the reason Odena’s article exists. Segmentation decoders and the diffusion U-Nets that followed mostly use resize + convolution; super-resolution mostly uses sub-pixel convolution with ICNR, because doing the arithmetic at low resolution matters when the output is 4× larger in each dimension. Transposed convolutions have not disappeared — they are still the cheapest learnable upsampler and still correct when k % s == 0 — but they are no longer the default, and choosing one now needs a reason. Whatever you pick, measure the artifact rather than eyeballing it: a phase-averaged residual takes ten lines and turns an argument into a number.
    
        
    # the honest decision procedure
if output_is_much_larger and compute_is_tight:
    layer = subpixel_conv(cin, cout, r, k=3); icnr_(layer[0].weight, r)
elif you_want_the_safe_default:
    layer = Sequential(Upsample(2, "nearest"), Conv2d(cin, cout, 3, padding=1))
else:
    layer = ConvTranspose2d(cin, cout, kernel_size=4, stride=2, padding=1)
    assert layer.kernel_size[0] % layer.stride[0] == 0     # non-negotiable

def checkerboard(v, s):                 # phase-averaged residual
    d = v - moving_average(v, 2*s + 1)
    m = [d[t::s].mean() for t in range(s)]
    return max(m) - min(m)              # 0.0 means clean. report it.
