What the number in the log actually is

A language model is trained by minimising the negative log probability it assigns to the next token, averaged over tokens. Write it out and the averaging is the whole problem: 

loss = (1/T) ∑ₐ −log p(tokenₜ | token₁…tokenₜ₋₁)

The sum is a property of the model and the data. The 1/T is a property of the tokeniser, because T is how many pieces the tokeniser chose to cut the data into. Two tokenisers cutting the same corpus produce different T, so they divide the same quantity by different numbers and print different results. This is not a subtlety and it is not small: the first card on the MEASURE tab holds the model completely fixed — it is the source's own conditional distribution, the best model that exists — and produces reported losses from 0.2519 to 3.0232 nats, a perplexity from 1.287 to 20.556, purely by regrouping.

Both directions are available, and both are exact rather than approximate. Group k symbols into one token and each prediction now carries k symbols of surprise, so the numerator is unchanged, T is divided by k, and the reported loss is multiplied by exactly k. Pad the token stream with a filler symbol that always follows — a separator, a byte-fallback marker, anything the model can predict with probability 1 — and you have added free predictions: the numerator is unchanged again, T is multiplied by r, and the reported loss is divided by exactly r. Choose k and r and the reported loss is whatever you like.

The quantity that survives

What does not move under either operation is the total: ∑ −log p over the whole corpus, which is the number of nats the model needs to describe the data. Divide it by something the tokeniser cannot touch — the number of bytes — and convert to bits, and you have a number that is a property of the model and the data alone: 

bits per byte = (loss per token / ln 2) × (tokens / bytes)

That is an identity, not a correction factor: the page asserts it holds to 1e-12 on every row of every table. Its meaning is compression. A model at 1.7482 bits per byte — the best row on this page — would let you store this corpus in 1.7482 bits per symbol; the source's entropy rate, 1.4500 bits per byte, is the floor no model of any tokenisation can go below, and the gap between them — the excess — is exactly how much worse than perfect the model is. It is the same idea as bits-per-character in the older character-LM literature, and it is why anyone comparing models across tokenisers reports it.

The reason to belabour this is that the failure is not a wash. Over 144 trained models the loss per token ranks model quality at AUC 0.369 against a chance value of 0.500 — it is not uninformative, it is anti-informative, and you would do markedly better by preferring the model with the higher loss. Meanwhile tokens per byte, an integer you can read off the tokeniser before you own a GPU, ranks at 0.718.

The part that is a control, not a complaint

It would be easy to leave that as “the loss is broken”, and it is not. Hold the tokeniser fixed and vary everything else — width, context, training budget, seed — and the loss per token ranks the same models perfectly: AUC 1.000 over 1,656 pairs, in all six tokenisers separately. Within one tokeniser, tokens per byte is a constant, so bits per byte is a fixed multiple of the loss and the two orderings are identical by construction. That is the honest statement: the number is fine, the comparison is not. Watching your own loss fall is meaningful. Comparing it to someone else's is not.

Why a coarser tokeniser can be a better model

The mechanism on this page is not a quirk of the construction. A transformer's context is a fixed number of tokens, so what the model can see is C × bytes-per-token bytes. The source here is order 3: a model that sees only two symbols of history is misspecified and has a floor of its own well above the entropy rate. At C = 2 the byte tokeniser sees 2.00 bytes and cannot represent the distribution at all; 24 BPE merges see 4.27 and can. The byte tokeniser posts the better loss per token — 1.4138 nats against 2.5851, a perplexity of 4.11 against 13.26 — and is the worse model, on all five pairwise comparisons that involve it.

Two controls stop that from being a story rather than a measurement. First, capacity: widen the byte model from 581 to 5,333 parameters, nearly four times the winner's 1,373, and it gets worse (2.0397 → 2.1171 bits per byte) — extra width with the wrong information in the window buys overfitting, not accuracy. Second, context: at C = 3 the byte tokeniser finally covers the order, wins on both numbers at 1.6734 bits per byte, and the inverted pairs collapse from 11 of 15 to 4 of 15, and to 2 of 15 at C = 4. So the ranking of two tokenisers is not a property of the tokenisers. It is a property of the tokenisers and the context length, which is one more thing the per-token number cannot encode.

Two things that stop bits per byte being the end of it

It has a noise floor, and this page's own table sits inside it. Give the estimator a model whose excess is exactly zero and 8,000 held-out symbols, and it still reports a mean absolute error of 0.0124 bits per byte, worst-of-24 0.0308. The two best rows of the headline table are 0.0099 apart — below even the mean floor — and the leading three sit within 0.0480 of each other. Naming a winner among them is reading noise. The one comparison the page is entitled to make is bytes against BPE, 0.2915, which is 9.47× the worst-case floor.

It is an upper bound whose slack depends on the tokeniser. A model over tokens defines a distribution over token sequences; a string usually has many. The encoder emits one, and the reported loss uses that one, so the reported bits per byte is −log₂ p(canonical path), while the model's own probability of the string is the sum over every path. Enumerating all of them shows nearly half of a BPE model's probability mass sitting on sequences its own encoder can never produce — 48.90% — worth 0.7144 bits per byte, while the same correction is 0.0000 for a byte tokeniser and 0.0041 for a fixed-block one. Correct for it and 6 of 15 pairwise comparisons change. So bits per byte fixes the unit and does not fully fix the comparison; it is the best number you can compute cheaply, not a canonical one.

The corollary nobody puts in a loss curve

Greedy longest-match encoding is not compositional: encoding a string is not encoding its halves and concatenating. On this page 60.7% of split points retokenise for a 48-merge vocabulary, 51.8% for a 24-merge one and 0.0% for a byte vocabulary. Every one of those is a prompt whose final tokens the model has never seen in that arrangement — the practical face of the same fact, and the reason a token-boundary bug shows up as an inexplicable quality drop and never as a worse validation loss.

So what to report

  • Bits per byte, or bits per character. One multiplication. It makes the number a statement about the data instead of about the vocabulary.
  • Tokens per byte, next to it. It is free, it explains most of the difference between two tokenisers, and it out-ranks the loss.
  • The context in bytes, C × bytes-per-token, because that is what actually changed when the vocabulary changed.
  • A floor for the comparison. Two bits-per-byte numbers closer together than the estimator's noise at your held-out size are one number.
  • Loss per token for your own curve, where it is a perfect ranker, and never across a tokeniser boundary.

The setup, so the numbers can be checked

Source: order-3 Markov chain, alphabet a–e, 125 states, from a seeded RNG; entropy rate 1.4500 bits per symbol by power iteration on the state chain. Corpora: 15,000 training and 8,000 held-out symbols. Model: token embedding (d = 8), C previous tokens concatenated, one tanh hidden layer (H = 24), softmax over the vocabulary, hand-written forward and backward, Adam for 300 steps at batch 128. Index 0 is a context-only pad and is not an output class, which is what makes the path enumeration sum to 1 exactly. Tokenisers: raw symbols; BPE vocabularies at 8, 24 and 48 merges; every 2-tuple; and the 12 most frequent 4-grams added whole. Encoding is greedy longest match throughout.

🔨 How it is built

1. A source with a computable floor

Everything on the page is a comparison against “how good could this be”, so the answer has to exist. An order-3 Markov chain over 5 symbols has 125 states; the stationary distribution is a power iteration run to 1e-16, and the entropy rate is ∑ π(s) H(P(·|s)) — an exact number, 1.4500 bits per symbol, not a held-out estimate. That turns every bits-per-byte reading into an excess, which is an absolute measure of model quality and the ground truth for the ranker study. The assertion suite checks ∑π = 1, that every conditional normalises, and that a long sample's empirical entropy lands on the exact value.

2. The identity needs no network, so it is shown first

The regrouping card uses the oracle byte model, which is the source itself. Blocking is implemented as a genuinely different summation — sum k terms into a block accumulator, then sum the blocks — rather than the same expression twice, so “the total description length is unchanged” is a measurement of floating-point rounding (7.9e-15 relative, and the bound is what to quote: summation-order rounding differs between engines) and not a tautology. All nine rows are scored on a symbol count divisible by every block size, because otherwise the truncated tail alone moves bits per byte in the fourth decimal and the identity would look approximate when it is exact.

3. Index 0 is a pad, not a class

The context needs something to hold before the first token. The first version of this page put a BOS symbol in the vocabulary as an ordinary output class, and the path enumeration then summed to 0.9926 instead of 1 — the missing 0.74% was probability the model had assigned to emitting BOS, which the encoder never does. That is a real bug with a real consequence (a byte tokeniser showed a 0.7% path deficit when it must be exactly zero), so the model now has V embedding rows and V−1 output classes. The enumeration sums to 1.0000000000000 and the byte tokeniser's deficit is 0.00%, both asserted.

4. A vocabulary that round-trips and is still wrong

BPE merge training works on a sequence of vocabulary ids, and symbol a lives at index a+1 because index 0 is the pad. The first version merged on raw symbol values, so every merged token was assembled from the wrong bytes and symbol 0 contributed the empty pad. Nothing complained: the vocabulary was still a set of valid byte strings, greedy encoding still round-tripped the corpus perfectly, an independently written encoder still agreed token for token, and the whole page rendered. It simply was not the frequent-pair vocabulary, and 24 merges bought 1.500 bytes per token instead of 2.133. The assertion that caught it is the one that does not share the assumption: reassemble the merged sequence and compare it with the corpus it came from. Every number on the page moved when it was fixed — including the headline, where the winner changed from the largest vocabulary to the middle one.

4. Two forward passes, one backward

fwd is the fast path used everywhere. nllAlt is written independently: it builds the context vector by pushing rather than indexing, accumulates the hidden pre-activation in the opposite loop order, and computes the loss as logsumexp(z) − zₕ instead of normalising a softmax. The central differences are taken on nllAlt, so a bug shared by the analytic gradient and the forward pass it was derived from cannot hide. The two agree to 1e-12 and the gradients to 1.2e-10 at initialisation and 4.1e-11 after training, checked at both points because a well-conditioned point can flatter a wrong derivative. An embedding used twice in one context accumulates both contributions — the += is load-bearing, and dropping it is the Day-67 bug in a new costume.

6. Every tokenisation, by dynamic programming

For a string s, the state is (symbols consumed, last C tokens) and the transitions are the tokens consistent with s from that position — including tokens that overshoot the end, which is what makes the mass sum to 1 rather than to the probability of stopping neatly. Softmaxes are cached by context key across all 15,625 strings, which is the only reason this runs in six seconds. The canonical path is scored separately by walking the encoder's own output. Two assertions carry the card: the enumeration must sum to 1, and the byte tokeniser's deficit must be exactly 0, since with one-symbol tokens there is only one path.

7. The ranker, and the control that saves the number

144 models over tokeniser × width × context × budget × seed, each scored against the exact excess bits per byte, with AUC computed by an explicit pair loop (ties count a half). The candidates deliberately include two numbers that need no training at all — tokens per byte and the parameter count — because a diagnostic that loses to one of those has a problem no amount of careful reporting fixes. The last block computes the same AUC within each tokeniser separately, which is what turns the finding from “the loss is meaningless” into the true and much narrower “the loss does not survive a change of unit”.

8. What the tests pin

56 assertions run in the page and 318 in Node against independently written reimplementations — the source conditionals recomputed, greedy encoding rewritten, the forward pass rewritten a third time, bits per byte recomputed from a raw byte count, AUC recomputed with its own pair loop, and the path enumeration re-derived by brute-force recursion over every token sequence rather than by dynamic programming. Several assertions exist purely to fail if the page drifts back to something it disproved: that the loss is anti-informative across tokenisers, that it is a perfect ranker within one, that the byte tokeniser has exactly zero path deficit, and that the top rows of the headline table are inside the noise floor.
