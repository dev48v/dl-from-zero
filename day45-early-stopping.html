DeepLearningFromZero · Day 45

🛑 Early Stopping — give a big enough network enough time and it will drive its training loss to zero by memorising the noise in your data. But the thing you actually care about — error on data it hasn’t seen — does something different: it falls while the net learns the real signal, reaches a minimum, then climbs back up as the net starts fitting quirks that don’t generalise. Plot both and you get the classic picture: a training curve sliding monotonically toward 0 and a validation curve shaped like a U, the gap between them widening — that gap is overfitting. Early stopping is the simplest, cheapest fix in all of deep learning: hold out a validation set, and watch its loss every epoch. Keep the weights from the best (lowest-val) epoch. When val hasn’t improved for patience epochs in a row — long enough that it’s a real upturn and not just noise — stop training and restore those best weights. A min-delta says how big an improvement has to be to “count,” so tiny wiggles don’t reset the clock. Why does it work as regularisation? Gradient descent grows the weights gradually; stopping early is a budget on how far it can walk — it keeps the effective model simpler, much like an L2 penalty, without touching the loss function. Below is a real over-capacity model (34 basis functions) fit by genuine gradient descent to 16 noisy points: watch the training MSE fall monotonically while the validation MSE U-turns live, the best-val epoch get marked, a patience slider move the stop point — and the held-out test error come out genuinely lower with early stopping than without.

🔨 Build it yourself

    
Early stopping is maybe fifteen lines of glue around your training loop, but the details — which metric, how patience really counts, min-delta, and above all restoring the best weights instead of keeping the last ones — are where people get it wrong. We build it from a naive loop up to the exact logic the framework callbacks use, then see the one-liners in Keras and PyTorch Lightning.

    
    
      
  1. 
        
    1
    The trap — “just train for N epochs”
    
        
    Pick a big epoch count, train, ship. The problem: there is no single right N. Too few and the model underfits; too many and it slides past its best point into overfitting, memorising the training noise. And the sweet spot moves with the model, the data, and the learning rate — you can’t guess it once and reuse it.
    
        
    for epoch in range(1000):        # a fixed, guessed budget
    train_one_epoch(model, train_loader)
# ship model  ->  but was 1000 too few, or way too many?
# no feedback loop = you find out only in production
    
      
    2. 
      
  2. 
        
    2
    Hold out a validation set — a proxy for “unseen”
    
        
    Split your labelled data into train / val / test. You train on train, and after every epoch you measure loss on val — data the optimiser never sees a gradient from. That val loss is your live estimate of generalisation. (Keep test sealed until the very end; the moment you tune to val, val stops being unseen — that’s what test is for.)
    
        
    train, val, test = split(data, [0.7, 0.15, 0.15])
# gradients come ONLY from train
# val loss  = live proxy for error on unseen data
# test set  = touched once, at the end, for the honest number
    
      
    3. 
      
  3. 
        
    3
    Watch val every epoch — and remember the best
    
        
    The core idea in one loop: after each epoch, evaluate val loss. If it’s the best you’ve seen, snapshot the model’s weights. That snapshot is the model you’ll actually keep. Everything else — patience, min-delta — is just deciding when to quit the loop; the snapshot is the payoff.
    
        
    best_val = float("inf"); best_state = None
for epoch in range(max_epochs):
    train_one_epoch(model, train_loader)
    v = evaluate(model, val_loader)
    if v < best_val:
        best_val = v
        best_state = copy.deepcopy(model.state_dict())   # remember it
    
      
    4. 
      
  4. 
        
    4
    Patience — don’t quit on a single bad epoch
    
        
    Val loss is noisy — it can tick up for an epoch or two and then keep falling. If you stopped at the first uptick you’d quit far too early. Patience is the fix: count how many epochs in a row have failed to beat the best. Only when that counter reaches patience do you conclude the upturn is real and stop. Reset the counter to 0 every time you find a new best.
    
        
    wait = 0
for epoch in range(max_epochs):
    train_one_epoch(model, train_loader)
    v = evaluate(model, val_loader)
    if v < best_val:
        best_val = v; best_state = deepcopy(model.state_dict()); wait = 0
    else:
        wait += 1
        if wait >= patience:            # N epochs with no new best
            break                         # the upturn is real -> stop
    
      
    5. 
      
  5. 
        
    5
    Min-delta — ignore improvements too small to matter
    
        
    Without it, a val drop of 0.00001 counts as “improvement,” resets patience, and keeps you grinding forever on noise. min-delta sets the smallest change that counts: an epoch only qualifies as a new best if it beats the record by more than min_delta. Bigger min-delta = stricter = stops sooner. It turns “did it improve?” into “did it improve enough?”
    
        
    if v < best_val - min_delta:        # must beat it by a margin
    best_val = v
    best_state = deepcopy(model.state_dict())
    wait = 0
else:
    wait += 1                        # tiny wiggles no longer reset the clock
    
      
    6. 
      
  6. 
        
    6
    Restore best weights — the step everyone forgets
    
        
    When the loop breaks, your model is sitting at the stop epoch — which is patience epochs past the best one, already a little overfit. If you ship it as-is you throw away the whole point. Load the snapshot back so the deployed weights are the best-val ones. In the demo, turning “restore” off visibly bumps the test error — that gap is exactly these patience wasted epochs.
    
        
    # loop just broke at the stop epoch (a bit past the best)
model.load_state_dict(best_state)    # <-- rewind to the best-val epoch
# THIS is the model you deploy.  Skip it and early stopping is half-done.
    
      
    7. 
      
  7. 
        
    7
    The whole thing, and the framework one-liners
    
        
    Put it together and it’s a tiny, reusable helper — which is exactly why every framework ships it as a callback. Keras’ EarlyStopping(restore_best_weights=True) and Lightning’s EarlyStopping callback are this same monitor / patience / min-delta / restore logic. Always set restore_best_weights=True (Keras defaults it to False — a classic footgun), and monitor the metric you actually care about (val_loss, or e.g. val_accuracy with mode="max").
    
        
    # Keras
cb = keras.callbacks.EarlyStopping(
        monitor="val_loss", patience=10,
        min_delta=1e-3, restore_best_weights=True)   # <- don't forget True
model.fit(X, y, validation_data=(Xv, yv), epochs=1000, callbacks=[cb])

# PyTorch Lightning
from lightning.pytorch.callbacks import EarlyStopping
trainer = Trainer(callbacks=[EarlyStopping(monitor="val_loss", patience=10)])

  8. 
        
    8
    Why it’s implicit regularisation — and its friends
    
        
    Gradient descent starts from small weights and grows them a little each step. Stopping early caps how far the weights can travel — so the effective model stays simpler. For a linear least-squares fit this is provably close to L2 / ridge regularisation, with the stop time playing the role of the penalty strength: fewer steps ↔ stronger shrinkage. That’s why it fights overfitting without adding a penalty term. It composes with the other regularisers — dropout, weight decay, data augmentation — and is nearly free, so it’s on by default in practically every serious training run. Its one cost: you spend a slice of data on validation.
    
        
    # small init  ->  GD grows ||w|| gradually  ->  stopping = a budget on ||w||
#   fewer steps  ~=  stronger L2 shrinkage   (early-stopping ~ ridge)
# pairs with: weight decay, dropout, data augmentation, label smoothing
# cost: a held-out val split.  benefit: free regularisation + no wasted compute

🎉 Day 45 of DeepLearningFromZero done.
Early stopping is the cheapest regulariser in deep learning. Give an over-capacity model enough epochs and its training loss marches to zero by memorising noise, while validation loss traces a U — down as it learns the signal, back up as it overfits. So you hold out a val set, watch its loss each epoch, keep the weights from the lowest-val epoch, and once it hasn’t improved by more than min-delta for patience epochs you stop and restore those best weights. Patience keeps a noisy uptick from stopping you too soon; min-delta stops tiny wiggles resetting the clock; restore-best-weights is the step that makes it actually work — without it you deploy the slightly-overfit stop epoch. It behaves like implicit L2: capping the number of GD steps caps how big the weights grow, keeping the model simpler for free. You watched a real 34-basis model fit 16 noisy points — train MSE monotone down, val MSE genuinely U-turning, and held-out test error lower with early stopping than without. 👉 Tomorrow, Day 46: Weight Decay & L2 Regularisation — the explicit version of the shrinkage early stopping gives you implicitly.
