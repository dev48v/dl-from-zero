🧩 Straight-through estimators — the backward pass of an operation that has no useful derivative. The bottleneck here is six binary units, h = sign(pre), and the task is built so that a discrete bottleneck is exactly the right model: the true conditional depends on x only through m binary features, so a zero-excess student provably exists, the teacher itself scores exactly 0, and the score is a mean KL from the true conditional above a conditional-entropy floor of 0.8161 nats over 4 classes with the whole 64-point input space enumerated. The honest derivative of that bottleneck is not small, it is exactly zero: reverse mode returns 0.0e+0 on all 42 parameters below the bottleneck, forward-mode automatic differentiation over dual numbers agrees at 0.0e+0, and a central difference reads exactly zero on 42 of 42 coordinates — an identity rather than a tolerance, because a perturbation that flips no code leaves the two forward passes bit-identical, and the page asserts that equivalence in both directions. Gradient descent on the encoder is therefore not slow, it is arithmetically the same thing as not training the encoder: the honest-gradient run and the frozen-encoder run land on 0.2890 with a gap of exactly 0.0e+0. The straight-through estimator replaces dh/dpre with 1, which is not an approximation of the derivative but the exact derivative of a different function, h = q(pre) + (pre − stopgrad(pre)) — the page builds that second path over duals and gets a bit-identical answer, 0.0e+0, with the routed gradient matching forward mode to 1.7e-14 where a central difference manages 4.8e-9. THE PAGE CHECKING ITSELF

An operation with no derivative, in the middle of a network

Plenty of things you want inside a model are not differentiable. Rounding a real number to a grid. Taking a sign. Picking the nearest entry of a codebook. Sampling a discrete latent. Choosing an integer. All of them share a shape: a forward pass that is piecewise constant. And a piecewise-constant function has a derivative — it is 0 — which is worse than having none at all, because 0 is a number that flows quietly through a backward pass and produces a run that looks like training and is not.

The MEASURE tab starts there because it is the whole reason the topic exists. Ask the honest backward pass for the gradient of the loss with respect to any parameter below the bottleneck and it returns exactly zero. Not 1e-12. Zero. Forward-mode differentiation over dual numbers, which never forms a step size and never traverses the graph the same way, returns exactly zero as well. And a central difference — the thing you would reach for to check — also returns exactly zero, which is the most interesting of the three, because it means the check agrees with the bug. The page turns that into an identity in both directions: a finite difference on an encoder parameter is exactly 0 if and only if the perturbation flipped no code, since with no flip the two forward passes are bit-identical and their difference is a subtraction of a number from itself.

So the honest gradient does not train the encoder. It does not train it slowly; it does not train it badly. The page runs the comparison and the two numbers are the same number: training on the honest gradient and freezing the encoder differ by exactly 0.

The straight-through estimator is not an approximation

The fix, from Hinton's 2012 lectures and then Bengio, Léonard and Courville (2013), is to lie in the backward pass: pretend the quantiser was the identity, and pass the incoming gradient through unchanged. It is usually described as an approximation to a derivative that does not exist, which makes it sound like a hack with an error term.

It is something more specific than that, and the page checks it as an identity. The routed gradient is the exact derivative of a different function — the one where the quantiser's output is treated as the input plus a constant shift:

h = q(pre) + (pre - stopgrad(pre))

The forward value is q(pre) + 0, so it is bit-identical to the quantised network. The derivative is 1, because the second term contributes 1 - 0. The page builds that path separately, over dual numbers, and gets the routed gradient back to the last bit: 0.0e+0. There is no error term. There is a different function, whose forward pass happens to coincide with the one you wanted, and whose gradient you are descending instead.

That reframing is what makes the rest of the page possible to reason about. The question is never how good an approximation is it. The question is whether the surrogate's descent directions get you somewhere on the objective you actually care about.

The test you would run cannot see the bug

Suppose the route is wrong — a sign flipped, an index off by one, a spurious gate. What would catch it? The natural answer is the one people reach for: take a step and see whether the loss goes down. On this page that test catches none of the seven broken routes. The sign-flipped one, which points the encoder in exactly the wrong direction, lowers the loss on every single trial.

The reason is a counting argument. Most of the parameters are not below the bottleneck. The decoder's gradient is correct in every variant — only the route is mutated — and a step that improves the decoder improves the loss regardless of what the encoder does. The encoder's contribution is not merely outvoted: applied on its own, at the same size, it does not move the deterministic loss at all on most trials, because the forward pass is piecewise constant and a small parameter change usually flips no code.

Which points at the control. The one loss the encoder route can descend is the smoothed one — the expectation over a stochastic bottleneck — and evaluated there, an encoder-only step separates the good routes from most of the bad ones. So does comparing the route's direction against the exact gradient of that relaxation. Neither catches everything, and the two they miss are instructive rather than embarrassing.

Wrong and harmful are different properties

Scaling the route by ten is unambiguously the wrong derivative, and it costs exactly nothing — the same final score, to 0.0e+0. Adam divides each coordinate by its own second moment, so a global factor cancels; what survives is eps against the gradient magnitude, and the page checks that residual against its closed form rather than asserting it is small. Meanwhile an off-by-one in the routing matrix, and having no route at all, both score better than the correct unclipped estimator.

That last comparison is the honest embarrassment of the method as usually stated. An unclipped straight-through estimator, on this task, is worse than not training the encoder. It is not worse because the derivative is wrong in some subtle way. It is worse because the route never shrinks: the gradient arriving at a unit is passed through at full strength no matter how far out the pre-activation has drifted, so the run keeps pushing, the pre-activations walk outward, and by the end most unit-input pairs sit far outside the range where the quantiser's decision is anywhere near the boundary. The forward pass has stopped listening and the backward pass has not noticed.

The clip is the method

Which is why the clipped variant — zero the route outside a window, the hardtanh derivative that BinaryConnect actually ships — is not a detail. On the default setting it more than halves the excess, and the best window on the ladder is tighter than the one everyone writes down. The mechanism is visible in the table: a wider window means a larger mean |pre| at the end, which means more of the backward pass sitting where the clip would have cut it.

And the cost of the clip is visible too, in the same table, which is the part usually left out: a tight window leaves whole units with no gradient for any input in the space — dead, permanently, since nothing can move them back inside. The best window on this page kills a third of the bottleneck and still wins. So the trade is not “clipping is good”; it is that saturating the route is worth more than the units it costs, up to a point that the sweep locates rather than assumes.

Having the right gradient is not the point

Because the bottleneck is narrow, this page can do what a real model cannot: enumerate every code and compute the exact gradient of the relaxed objective. Two independent forms of that derivative — a marginal difference and a score-function sum — agree, the code weights sum to one, the score has mean zero, and central differences of the relaxed loss (which is genuinely smooth) confirm it.

So we can ask the question directly. The exact gradient wins its own objective, comfortably. It does not win the model you deploy: a clipped straight-through estimator gets a better hard score at a small fraction of the cost, and the cost ratio is not a constant — it is the number of codes, which is exponential in the bottleneck width, so at any realistic size the exact gradient is not on the menu at all.

And when the same reasoning is turned into a ranker it inverts. Over a pool of trained configurations, agreement with the exact gradient at initialisation ranks final quality below a coin, and inside a single window-and-rate cell it carries no signal at all. The configurations whose route most resembles the exact derivative are the unclipped ones, which is precisely why they lose. Meanwhile the training loss you were already watching ranks them well. That is not a reason to stop reasoning about gradients; it is a reason not to treat “my estimator agrees with the true gradient” as evidence that the run will work.

A claim this page came to make and could not

The two ways people write the trick look different in floating point: q(x) + (x - x.detach()) is exact by construction, while x + (q(x) - x).detach() is a rounded sum and looked like it should occasionally land a bit off. It does not. Over 280,000 pre-activations at seven grid sizes the second idiom reproduces q(x) exactly every time, and there is a reason: q - x is computed exactly whenever |x| is not tiny, and when |x| is tiny the rounding error of q - x is at most half an ulp of q, so adding x back rounds to q. The page keeps the measurement and drops the claim.

What to take away

  • A piecewise-constant forward pass has an exactly-zero gradient, and a finite-difference check agrees with it. There is no tolerance to tighten.
  • The straight-through estimator is the exact gradient of a shifted-by-a-constant surrogate, not an approximation with an error term. Write it as q(x) + (x - x.detach()).
  • “One step lowered the loss” is not evidence that the route is right. Test the encoder alone, and test it on the smoothed loss, which is the only one it can descend.
  • Being the wrong derivative and being harmful are separate properties: under Adam a global mis-scale is free, and no route at all can beat an unclipped one.
  • Clip the route. The window is not a hyperparameter you can leave at its default and it is not free — it kills units — but saturating the route is what keeps the forward pass and the backward pass talking about the same thing.
  • Agreement with an exact gradient, where you can even compute one, does not predict which run ends up better.

Build it: one quantiser, four backward passes

Everything on this page runs from one engine block with no libraries, no DOM access and no clock. What follows is the shape of it.

1 · The quantiser, and the two limits that make it testable

One formula for every grid size, so the fine-grid limit and the no-bottleneck control are the same code path rather than a special case.

function quant(v, L){
  if (L <= 0) return v;                        // the identity: the no-bottleneck control
  if (L >= 1e9) return v < -1 ? -1 : v > 1 ? 1 : v;   // the clamp: the fine-grid limit
  var step = 2 / (L - 1);
  var idx  = Math.round((v + 1) / step);
  if (idx < 0) idx = 0;
  if (idx > L - 1) idx = L - 1;
  return -1 + idx * step;
}

At L = 2 this is a sign with sign(0) = +1. Its derivative is 0 everywhere it exists. Nothing about that changes as L grows: a finer grid is still piecewise constant.

2 · A task where the bottleneck is the right model

If the discrete bottleneck cannot express the answer, every result is confounded by that. So build the teacher through a bottleneck of the same width: m binary features of the input, then a small decoder.

t_j(x) = sign(U_j . x + c_j)                 // m binary features
p*(y|x) = softmax( V2 . tanh(V1 . t(x) + d1) + d2 )

The input space is {-1,+1}^6, all 64 points, so every expectation over x is a sum and not a sample. The score is the mean KL from p*, which is exactly 0 for a student that copies the teacher and provably non-negative for everything else. The floor is the conditional entropy, computed, not estimated.

3 · The honest backward pass, and the one line that is a choice

Everything above the bottleneck is an ordinary backward pass. The only decision is what the backward pass claims dh/dpre is:

for (j = 0; j < m; j++){
  var f = routeFactor(mode, rec.pre[j], rec.h[j], dh[j], clip);
  var dp = dh[j] * f;
  g.b1[j] += dp;
  for (i = 0; i < x.length; i++) g.W1[j][i] += dp * x[i];
}
"true" -> 0                              // the honest answer
"ste"  -> 1                              // straight through
"clip" -> |pre| <= c ? 1 : 0             // the hardtanh derivative

Seven more values of mode exist only so the page can ask whether any diagnostic notices them. Keeping them in one switch, rather than in seven copies of the backward pass, is what makes the comparison a comparison.

4 · Check the gradient with something exact, at initialisation

Finite differences are the wrong instrument twice over here. On the encoder they return exactly zero, agreeing with the bug. On the decoder they agree to about 5e-9, which is a finite-difference floor and not a statement about the code. So the page carries a forward-mode pass over dual numbers — value and derivative side by side, one seed per parameter, no step size anywhere — and the quantiser's dual derivative is the same switch:

var qv = quant(s, L), f;
if (opt.hMode === "sgA"){ hv[j] = qv + (s - s); hd[j] = sd; }   // the detach idiom
else { f = opt.hMode === "true" ? 0 : 1; hv[j] = qv; hd[j] = f * sd; }

Reverse mode and forward mode then agree to about 1e-14, which is arithmetic rounding, and the sgA path agrees with the routed gradient bit for bit. Both checks run at initialisation. Checking at convergence is how you get a false failure: the true gradient there is already so small that any difference test is measuring its own floor.

5 · The exact gradient of the relaxation, by enumeration

Make the bottleneck stochastic — h_j = +1 with probability sigmoid(pre_j) — and the model becomes a distribution over 2^m codes. Now the expected loss is smooth and its gradient exists. With m small it can be summed rather than sampled, two independent ways:

// marginal form: dLbar/dp_j = E over h_-j [ loss(h_j=+1) - loss(h_j=-1) ]
// score form:    dLbar/dpre_j = sum_h w(h) * loss(h) * (h_j==1 ? 1-p_j : -p_j)

They agree to 1e-13, the weights sum to 1, and the score has mean zero — three identities that would break loudly if the enumeration were wrong. Central differences of the relaxed loss confirm the result, and here they are legitimate, because this loss really is differentiable.

6 · Price it

The exact gradient costs one decoder pass per code, so 2^m per example against the estimator's one. The page prints that column next to the scores, because a method that wins on quality and loses by an exponential factor on cost has not won.

7 · Two tests and a control

// what people run: step everything, did the loss fall?
var nA = copyNet(net); sgdStep(nA, g, probeLr, allParams);
if (dataNLL(nA, batch) < L0) descend++;

// the control: step the ENCODER only, and judge it on the smoothed loss
var nB = copyNet(net); sgdStep(nB, g, probeLr, encoderParams);
if (dataNLL(nB, batch) !== L0) moved++;              // usually it does not move at all
if (relaxLoss(nB, batch, CS) < R0) descRelax++;

The moved counter is worth keeping even though it is not a test: it is the reason the first test is useless. A piecewise-constant forward pass does not respond to a small encoder step, so there is nothing for a local check to read.

8 · Assert identities, not thresholds

The page's own self-check is 501 assertions, and the ones that matter are equalities rather than tolerances: the honest encoder gradient is === 0; the detach idiom is === 0 away from the routed gradient; the honest-gradient run and the frozen run differ by === 0; an infinite clip window is the plain estimator bit for bit; flipping the route negates the cosine exactly; a finite difference is zero exactly when no code flipped. A threshold picked to pass at one slider setting is a failure waiting for a different one.
